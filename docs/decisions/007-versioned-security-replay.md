# ADR 007: Versioned security replay evidence

Posted financial facts, legs and initial lot allocations are evidence and are never rewritten by a historical security change. A new backdated buy/sell or correction is accepted only inside a workspace-serialized, idempotent transaction after chronological replay proves all later cash balances, FIFO disposals and basis remain valid. The correction link marks a source inactive and retains its original same-day order.

Schema 5 stores one immutable full-account replay run after each historical change and each later append. A run records the active-source fingerprint, FIFO calculation version, lots, per-event gains and allocations. Reports use the newest matching run and reject a stale fingerprint or version. The old `transactions.realized_gain` and `lot_allocations` remain as the calculation made when originally posted; API consumers use `current_realized_gain` or `current_calculation` for current results. This preserves the trail when a historical buy changes a later sale's gain without editing that sale.

The projection is JSON and currently recalculates a whole account. Large histories need benchmarking and likely paged or checkpointed replay before production scale. A mismatch requires an independently reviewed forward repair that appends a new run after reconciliation; silently regenerating or overwriting evidence is forbidden. Trade-linked fills are blocked from this correction path until the journal relationship has its own revision contract. Retroactive opening entries and unknown-basis resolution remain separate work.
