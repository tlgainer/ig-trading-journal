# Internal explicit AI generation coordination

`AiGeneration::run` now connects trusted server setup, exact approved complete-input counting, verified reservation and one-time Responses delivery. This is an internal operation only: no admin Generate summary control, REST route, automatic schedule or publication is added. It remains disabled by default. Source stays schema 18; no new SQL or ZIP for this slice.

The caller supplies an explicitly authorized owner's spending service, workspace, saved approval ID, stable operation key and full output-token ceiling. Browser-supplied prompts, pricing, model evidence, token counts or arbitrary destinations are not accepted. Current selected-model evidence is read from the [server configuration source](ai-server-evidence.md), revalidated after counting and again before sending. Existing count, reservation and dispatch checks enforce consent, approval ownership, model/credential identity, dated prices, fresh complete-input bounds and the shared monthly budget.

The spending service coordinates each workspace/operation key with a short, non-waiting MySQL named-lock acquisition. That operation lock stays held over count/reserve/send; no database transaction is held across HTTP. Shared spending transactions keep their separate existing lock and atomic audits. Overlapping calls, including re-entry on the same connection, fail before another count. Operation identities and lock names use hashes; every request lookup is workspace scoped. A conflicting actor, approval ID or output ceiling cannot reuse an existing key.

If a request already exists, a retry returns only its state and request ID. It does not count, replace its manifest, reserve again or send. This includes an abandoned reservation before dispatch, a dispatched/uncertain request and settled or quarantined work. An abandoned reserved request needs an explicit future cancel/recovery action; retrying this coordinator never silently dispatches it. Key/model/policy changes do not cause an existing operation to be regenerated.

For a new operation, counting still requires trusted zero-charge/access evidence. Counting failure creates no reservation; a later explicit attempt can count again after coordination is released. There is no persistent pre-reservation attempt ledger or automated retry. A process crash before reservation may therefore permit another explicitly requested count; unknown/paid counting remains unsupported. After reservation, dispatch is claimed exactly once and delivery uncertainty preserves the existing conservative hold.

Results contain only state and, when available, request ID. Provider error text, prompts, usage, credentials and model evidence are excluded. Known usage settlement does not imply suitable review output. Publication remains the separate guarded `AiReviews::publish_received` operation using the stored completed receipt; publication retry makes no provider call and does not refund known charges.

Tests intercept both fixed HTTPS endpoints with synthetic evidence and responses. They cover default-off operation, exact count/send bodies, successful settlement without automatic publication, safe publication from stored receipts, unchanged retries, conflicting context, retained uncertain holds, abandoned reservations, revoked consent, foreign approvals and overlapping same/separate database connections. Real credentials, model access, counting cost and production hosting remain unverified.

Next: verified evidence acquisition, owner enable/generation/status/publication controls and operational recovery. There is no newly usable summary generation button in the current admin screens. Keep the server processing switch off until those controls and acceptance gates are complete.
